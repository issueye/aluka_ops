# Aluka Ops 开发优化计划

## 目标

围绕当前项目分析结论，本计划聚焦三个方向：提升架构可维护性、强化生产安全与稳定性、补齐工程化与测试能力。目标是在不改变现有核心产品形态的前提下，把项目从“功能可用”推进到“可持续迭代、可验证交付、可生产部署”。

## 优先级总览

| 优先级 | 方向 | 主要收益 |
| --- | --- | --- |
| P0 | 认证安全、配置保护、构建可用性 | 降低生产误用和不可交付风险 |
| P1 | Router/Service 拆分、错误可见性、测试补强 | 降低维护成本，提高变更信心 |
| P2 | 部署工程化、并发能力、集群能力完善 | 支撑更复杂运行场景 |
| P3 | 长期架构治理与可观测性 | 提升规模化演进能力 |

## 阶段一：生产安全与交付底线

建议周期：1-2 周。

### 1. 强化认证默认策略

当前风险：默认密码为空时 API 自动放行，容易在生产环境误暴露。

计划：

- 引入显式安全模式：`-allow-no-auth` 或 `ALUKA_ALLOW_NO_AUTH=true`。
- 未配置密码且未显式允许无鉴权时，启动失败并输出明确错误。
- Agent/Controller 模式未配置共享密钥且未显式允许空密钥时，启动失败。
- 登录、Token 校验、远程 Agent 代理请求统一走鉴权边界。
- 在 README 中补充首次部署安全配置说明。

验收标准：

- 未设置密码且未显式允许无鉴权时，服务拒绝启动。
- Agent/Controller 模式未设置共享密钥且未显式允许空密钥时，服务拒绝启动。
- 本地开发仍可通过显式开关无密码启动。
- 相关中间件和配置加载逻辑有单元测试覆盖。

### 2. 修复构建产物依赖风险

当前风险：前端 `dist/` 不存在时后端嵌入编译失败，影响新环境构建。

计划：

- 增加统一构建脚本，先构建 `web`，再构建 Go 二进制。
- 增加空白或占位嵌入策略，保证开发态后端可独立编译。
- 明确 `go build`、`npm build`、全量构建三种路径。

验收标准：

- 新克隆仓库按文档命令可完成构建。
- 前端未构建时，后端开发模式有明确提示，不出现难以理解的 embed 错误。
- CI 可验证全量构建流程。

### 3. 提升关键错误可见性

当前风险：审计日志、后台任务、状态更新中的错误可能被静默忽略。

计划：

- 梳理审计、健康检查、进程管理、日志流、Agent 心跳中的错误处理。
- 对不可恢复错误返回到调用方，对可恢复错误写入结构化日志。
- 增加统一错误分类：用户输入错误、依赖错误、系统错误、后台任务错误。

验收标准：

- 审计写入失败有日志和可观测信号。
- 后台任务失败不会悄悄丢失，至少进入错误日志。
- Controller 层返回错误格式保持一致。

## 阶段二：架构拆分与可维护性

建议周期：2-4 周。

### 1. 拆分路由初始化

当前问题：`router` 层承担依赖创建、路由注册、后台任务组装等多重职责。

计划：

- 将依赖初始化拆为 `bootstrap` 或 `app` 层。
- 将 HTTP 路由注册按领域拆分：服务、站点、文件、运行时、终端、隧道、审计、集群。
- 保留统一的中间件装配入口，避免各模块重复处理鉴权和审计。

建议结构：

```text
internal/app          # 应用组装、生命周期管理
internal/router       # 只负责 HTTP 路由挂载
internal/controller   # 请求解析与响应
internal/service      # 业务编排
```

验收标准：

- `router` 不直接创建大量底层依赖。
- 单个领域路由可以独立阅读和测试。
- `cmd/server/main.go` 只保留配置加载、应用启动、退出处理。

### 2. 收敛 Service 动态依赖注入

当前问题：部分 Service 通过 Setter 注入运行时依赖，依赖关系不够显式。

计划：

- 为核心 Service 定义构造函数参数或依赖结构体。
- 将可选依赖明确建模为接口或配置项。
- 禁止新增无约束 Setter，除非用于测试替换或生命周期回调。

验收标准：

- 核心 Service 的依赖可以从构造函数直接看出。
- 单元测试可以通过 mock/fake 注入依赖。
- 依赖初始化顺序由 `app` 层统一管理。

### 3. 按领域治理大包

当前问题：部分包功能跨度较大，随着功能增长会形成维护瓶颈。

计划：

- 先以“高变更、高耦合、高测试难度”为指标选择拆分对象。
- 优先拆分进程管理、文件管理、网关、隧道、终端等基础能力。
- 每次拆分只移动边界清晰的代码，避免行为重写。

验收标准：

- 拆分提交保持行为等价。
- 包之间依赖方向清晰，避免循环引用。
- 公共接口数量少且职责明确。

## 阶段三：测试与质量门禁

建议周期：2-3 周，可与阶段二并行推进。

### 1. 补齐后端核心测试

重点覆盖：

- 配置加载优先级：命令行 > 环境变量 > 默认值。
- 鉴权中间件：无密码、错误密码、有效 Token、远程代理。
- Service 生命周期：启动、停止、重启、健康检查注册、异常退出。
- Repository 边界：SQLite 迁移、唯一约束、状态更新。

验收标准：

- 核心配置、鉴权、服务生命周期都有单元测试。
- 关键 Repository 使用临时 SQLite 测试库验证。
- 新增修复类提交必须附带回归测试。

### 2. 建立前端测试基线

重点覆盖：

- API client 的本地/远程 Agent 路径拼接。
- 登录态与认证失败处理。
- 服务、文件、终端等关键页面的基础交互。

验收标准：

- 至少引入组件测试或轻量 E2E 测试之一。
- 远程 Agent 代理路径有自动化测试，避免回归。
- 构建和 lint 纳入 CI。

### 3. 引入 CI 质量门禁

计划：

- 增加 GitHub Actions 或等价 CI。
- 后端执行 `go test ./...`。
- 前端执行安装、lint、build。
- 全量构建验证单二进制产物。

验收标准：

- 每次提交或 PR 自动执行测试与构建。
- CI 失败能准确定位后端、前端或打包阶段。

## 阶段四：部署工程化与运行稳定性

建议周期：2-4 周。

### 1. 增加标准部署资产

计划：

- 增加 `Makefile`，统一常用命令。
- 增加 `Dockerfile`，支持单容器部署。
- 增加示例 `docker-compose.yml`，挂载 `data/` 目录。
- 补充 systemd 服务示例。

建议命令：

```text
make dev-backend
make dev-web
make build-web
make build
make test
```

验收标准：

- 本地、Docker、systemd 三种部署路径文档清晰。
- 数据目录、端口、密码、运行模式都可通过环境变量配置。

### 2. 优化 SQLite 并发与持久状态

当前风险：SQLite 并发上限较低，重启风暴保护仅内存态。

计划：

- 检查 SQLite WAL、连接池、busy timeout 配置。
- 将服务重启风暴计数或冷却窗口持久化，避免进程重启后失效。
- 对高频写入点做节流或批量写入评估。

验收标准：

- SQLite 配置适合单机运维面板写入模式。
- 异常服务不会因主进程重启绕过保护。
- 高频操作有明确日志和限流策略。

### 3. 明确 Agent/Controller 协议边界

计划：

- 定义 Agent 心跳、状态同步、代理请求、错误返回的稳定协议。
- 记录版本字段，支持后续协议兼容。
- 梳理 Controller 对离线 Agent、超时 Agent、异常返回的处理策略。

验收标准：

- Agent/Controller 交互有文档化协议。
- 协议变更有兼容策略。
- 远程调用错误在前端可区分网络错误、鉴权错误、业务错误。

## 阶段五：可观测性与长期演进

建议周期：持续推进。

### 1. 结构化日志与事件追踪

计划：

- 统一日志字段：request_id、agent_id、service_id、operation、duration、error。
- 对服务启停、文件操作、终端连接、隧道变更输出结构化事件。
- 审计日志与系统日志保持关联字段。

验收标准：

- 能按 request_id 追踪一次用户操作。
- 能按 service_id 追踪服务生命周期事件。

### 2. 指标与健康状态

计划：

- 增加内部健康端点，区分进程存活、数据库可用、后台任务可用。
- 暴露关键指标：服务数量、运行中服务数、Agent 在线数、请求错误数、后台任务错误数。
- 前端 Dashboard 区分“未知、正常、异常、降级”。

验收标准：

- 运维人员可以快速判断系统自身是否健康。
- Agent 离线、数据库异常、后台任务失败有不同状态。

### 3. API 合约治理

计划：

- 为前后端共享 API 增加 OpenAPI 或轻量 schema。
- 前端 API client 从合约生成或至少由类型集中管理。
- 对 breaking change 建立版本说明。

验收标准：

- 新接口有请求/响应类型定义。
- 前后端字段变更不再依赖人工同步。

## 推荐执行顺序

1. P0 安全启动策略与构建流程修复。
2. CI 基线：后端测试、前端构建、全量打包。
3. 拆分 `router` 初始化，把应用组装移入独立层。
4. 补齐鉴权、配置、服务生命周期测试。
5. 收敛 Service 依赖注入方式。
6. 增加 Docker、Makefile、部署文档。
7. 优化 SQLite 与重启风暴保护。
8. 文档化 Agent/Controller 协议。
9. 推进结构化日志、健康指标和 API 合约治理。

## 近期里程碑

### M1：可安全部署

范围：认证默认策略、构建脚本、基础 CI、部署文档。

交付物：

- 安全配置策略落地。
- 新环境可一键构建。
- CI 能跑通后端测试和前端构建。
- README 包含最小生产部署路径。

### M2：核心架构可维护

范围：`app` 组装层、路由按领域拆分、Service 依赖显式化。

交付物：

- `router` 职责收敛。
- 核心 Service 构造关系清晰。
- 配置、鉴权、服务生命周期测试覆盖。

### M3：运行更稳定

范围：SQLite 配置、重启风暴保护持久化、后台错误可见性、Agent 协议文档。

交付物：

- 高频写入和异常重启有保护策略。
- 后台错误可观测。
- Agent/Controller 交互边界明确。

## 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 架构拆分引入行为回归 | 每次只移动清晰边界，先补测试再拆分 |
| 安全策略影响开发便利性 | 提供显式开发开关，生产默认安全 |
| CI 初期引入大量失败 | 先建立最小门禁，再逐步加 lint 和 E2E |
| Docker 化影响本地数据路径 | 数据目录强制外置挂载，并在文档中说明 |
| Agent 协议变化影响兼容 | 增加协议版本和兼容处理 |

## 非目标

短期内不建议同时推进以下事项：

- 重写前后端技术栈。
- 将单体拆成微服务。
- 引入复杂分布式数据库。
- 大规模 UI 重设计。
- 在没有测试保护的情况下重写核心进程管理逻辑。

## 成功标准

完成以上计划后，项目应达到以下状态：

- 新环境可以按文档稳定构建和部署。
- 生产环境不会默认无鉴权暴露 API。
- 核心服务生命周期、鉴权、配置加载有自动化测试保护。
- 路由、应用组装、业务服务职责边界清晰。
- 常见运行异常能通过日志、审计或健康状态定位。
- Agent/Controller 演进有明确协议边界。
